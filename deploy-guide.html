Two Domains, One Afternoon

Getting the portfolio onto chantsolutions.com and Sipra onto getsipra.app. Part one you can do today — the code exists. Part two needs three pages written first.

Part 1 · chantsolutions.com Part 2 · getsipra.app App Store URLs
Part 1

chantsolutions.com

The portfolio is a Node server with a SQLite database, so it needs a host that runs a real process and gives you a disk that survives deploys. Render fits and is the shortest path. Railway or Fly work the same way if you prefer them.

  1. Push the project to GitHub

    From the unzipped folder. The .gitignore already excludes data/ and node_modules/, so no database or secret goes up.

    git init
git add .
git commit -m "ChantSolutions portfolio"
git branch -M main
git remote add origin https://github.com/<you>/chantsolutions.git
git push -u origin main

  2. Check it runs locally before anything else

    From the unzipped folder. If it works here it will work on Render, and you will have found any problem while it is still cheap to fix.

    node build.js
node server.js     # open http://localhost:3000, then Ctrl+C

  3. Create everything from the Blueprint

    The repo ships a render.yaml. In Render choose New → Blueprint, point it at the repo, and Apply. That one file creates the web service, mounts the persistent disk at /data, and sets every environment variable — so there is nothing to remember and nothing to mistype.

    Render will prompt you for exactly one value: ADMIN_EMAIL. Use the address you want the Moderator badge on.

    Set for you by the BlueprintValue
    Disk1 GB mounted at /data
    DB_PATH/data/portfolio.db
    TRUST_PROXY1 — Secure cookies, HSTS, real client address
    SESSION_SECRETgenerated by Render and kept
    NODE_VERSION22 — node:sqlite is built in from 22
    Health check/api/health
    Why the Blueprint, and not the dashboard

    Two of the settings are load-bearing and easy to miss by hand. Without the disk, every deploy silently wipes the guestbook — every account, note and reaction, no error, site still loading. And a SESSION_SECRET added after launch signs everyone out the moment you set it. Letting the file do it removes both.

    Render's free plan has no persistent disk, so the plan is set to starter. If you downgrade later, you lose the database.

  4. Deploy and check the temporary address

    Render gives you something like chantsolutions.onrender.com. Open it and confirm the page loads, the Library and Privacy tabs work, and you can create an account. Fix anything broken here, before DNS is involved.

  5. Add the custom domain in Render

    Service → Settings → Custom Domains. Add both chantsolutions.com and www.chantsolutions.com. Render then shows you the exact DNS values to use — use the ones it shows you, not the examples below.

  6. Add the DNS records at your registrar

    Wherever you bought the domain, in its DNS settings:

    TypeHostPoints to
    A@the IP address Render displays
    CNAMEwwwchantsolutions.onrender.com

    Delete any existing A, AAAA or CNAME on those hosts first — a leftover parking record from the registrar will quietly win. Some registrars call the apex record ALIAS or ANAME instead of A; either is fine.

  7. Wait for the certificate

    Render verifies the records and issues SSL automatically. Usually minutes, occasionally an hour. Until it finishes you may see a certificate warning — that is expected, not a mistake you made.

  8. Claim your moderator account

    Once the domain is live, sign up on the guestbook using the address you set as ADMIN_EMAIL. That is what grants the Moderator badge and the ability to delete anyone's note. There is no other way to get it, and no password reset if you lose it.

    Before you tell anyone about it

    Sign in, post a note, react to it, then open your account panel and download your data export. If the file comes back with your account in it, the whole stack is working — server, disk, sessions, and the privacy controls all at once.

Part 2

getsipra.app

Different problem. There is no Sipra website yet, so there is nothing to point the domain at. The app stores need three specific pages, and two of them are mandatory — Apple and Google will both reject a submission without a working privacy policy URL.

What has to exist before the domain matters

  1. A privacy policy page. Required by Apple and Google. Must describe what Sipra actually collects — Google sign-in, Firebase, and whatever the Cloud Function sends to the AI provider.
  2. A support page. Required by Apple. Needs a real, monitored way to reach you.
  3. A landing page. Optional for the stores, but it is what the domain is for.

  1. Host it on Firebase, since Sipra already lives there

    You are already paying the Firebase tax for Sipra's backend, so hosting the site there costs nothing extra, needs no second account, and includes SSL. From a new folder:

    npm install -g firebase-tools
firebase login
firebase init hosting
firebase deploy --only hosting

    Pick the existing Sipra project when it asks. Use public as the directory, and answer no to the single-page-app rewrite so /privacy and /support stay real URLs.

  2. Add the domain in the Firebase console

    Hosting → Add custom domain. Enter getsipra.app. Firebase gives you a TXT record to prove you own it, then A records to point at it.

    TypeHostPoints to
    TXT@the verification string Firebase shows
    A@both IPs Firebase lists

    Leave the TXT record in place permanently. Removing it after verification can un-verify the domain later.

  3. Expect it to look broken until SSL finishes

    .app domains cannot fall back to HTTP

    Google runs the .app registry and put the whole TLD on the browser HSTS preload list. Every major browser refuses plain HTTP on any .app address, permanently, with no click-through warning.

    So between pointing DNS and the certificate being issued, getsipra.app will look completely dead rather than merely insecure. That is the TLD working as designed. Firebase says allow up to 24 hours; it is usually a few. Do not start re-pointing DNS in the meantime.

  4. Add in-app account deletion before you submit

    Sipra offers Google sign-in, which creates accounts, and Apple requires any app that creates accounts to let people delete them from inside the app. A link to email you does not satisfy it. This is a common rejection reason and it is easier to build before submission than during review.

The three URLs the stores ask for

Privacy Policy URLApple & Googlehttps://getsipra.app/privacy

Do not reuse the portfolio's privacy page

The page at chantsolutions.com/#/privacy describes the guestbook: an email, a display name, a password hash, a session, a security log. Sipra collects something different — Google sign-in, Firebase, and drill content passing through a Cloud Function to an AI provider.

Submitting the wrong one is a rejection risk, and more importantly it is an inaccurate public statement about how you handle someone's data. Sipra needs its own.

Google Play also wants that same privacy link inside the app itself, not only in the Play Console listing. And the page must stay publicly reachable with no login, not a PDF, and not blocked by region.
